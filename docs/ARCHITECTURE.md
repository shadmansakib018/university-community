# Architecture — University Community

Status: Approved · M1 implemented · Last updated: 2026-10-12
Related: [PRD.md](PRD.md) · [DATABASE.md](DATABASE.md) · [IMPLEMENTATION_PLAN.md](IMPLEMENTATION_PLAN.md)

## 1. Overview

A single-page React app talks directly to Supabase, which handles Postgres, Auth and the auto-generated Data API. There is no custom backend server. **Row Level Security in Postgres is the authorization layer**. The frontend only mirrors those rules for UX.

```
Browser (React SPA on Vercel)
  └─ supabase-js (publishable key + user JWT)
       ├─ Supabase Auth   — sign up, sign in, email confirm, password reset
       └─ Data API (PostgREST)
            └─ Postgres: GRANTs → RLS policies → CHECK constraints → triggers
```

## 4. Layering rules

1. **Pages** compose hooks and components. They hold no Supabase calls.
2. **Components** are presentational. They receive data and callbacks through props and never import `supabase` or `api.ts`.
3. **Hooks** own async state (`data`, `isLoading`, `error`, `refetch`) and call `api.ts`.
4. **`api.ts`** functions are the only code that touches `supabase`. They return typed domain objects and throw a normalized `AppError`.
5. **`src/lib/supabase.ts`** is the single typed client, `createClient<Database>(url, key)`. It fails fast with a clear message if the env vars are missing.

This keeps UI testable with mocked hooks and keeps data access testable with a mocked client.

**State management**: an `AuthProvider` React context holds the session and the user's profile. Everything else is local or hook state. No global store and no query library in the MVP. If cache invalidation gets painful in M4, TanStack Query is the upgrade path, and it would need approval.

## 5. Routing

| Path | Access | Page |
|---|---|---|
| `/` | public (signed-in users → `/dashboard`) | Landing |
| `/signup` | public-only | Sign up |
| `/login` | public-only | Log in |
| `/forgot-password` | public-only | Request reset email |
| `/reset-password` | recovery session | Set new password |
| `/auth/callback` | public | Email confirmation landing → `/dashboard` |
| `/dashboard` | protected | Joined groups |
| `/discover` | protected | University search |
| `/groups/:groupId` | protected | Group feed (or join prompt for non-members) |
| `/groups/:groupId/posts/:postId` | protected | Post + comments |
| `/settings` | protected | Profile and account |
| `*` | any | 404 |

*(M2)* `RequireAuth` wraps protected routes. In M1 the routes are open and use a mock user. While auth is initializing, it renders a loading state, never a flash of the login page. When signed out, it redirects to `/login?redirectTo=<path>`. `redirectTo` is accepted only if it is a relative in-app path, which prevents open redirects.

## 6. Authentication flow

1. **Sign up**: `supabase.auth.signUp({ email, password, options: { data: { display_name, student_status }, emailRedirectTo: <origin>/auth/callback } })`.
2. A Postgres trigger (`handle_new_user`, SECURITY DEFINER) creates the `profiles` row from that metadata. It validates and trims the values and falls back to safe defaults, so a bad payload can't block sign-up or write invalid data.
3. **Confirm**: the email link lands on `/auth/callback`. supabase-js detects the session in the URL, and the app redirects to the dashboard.
4. **Session**: supabase-js persists the session in localStorage and refreshes tokens. `AuthProvider` subscribes to `onAuthStateChange`.
5. **Reset**: `resetPasswordForEmail(email, { redirectTo: <origin>/reset-password })`. On the `PASSWORD_RECOVERY` event the page shows the new-password form and calls `updateUser({ password })`.
6. **Log out**: `signOut()` clears local state and goes to `/`.

Supabase dashboard configuration (manual, documented in M2/M5): Site URL plus allowed redirect URLs for `http://localhost:5173/**` and the Vercel domain.

## 7. Error, loading and empty states

- Shared `LoadingState` (skeletons), `EmptyState` (icon, message, CTA) and `ErrorState` (message plus Retry) components are used by every data view.
- `lib/errors.ts` maps Postgres/PostgREST codes to friendly text, e.g. `23505` unique violation → "You've already joined this group", `42501` / RLS denial → "You don't have permission to do that", and check violations → field-level messages.
- Mutations show inline pending state on the triggering button and a toast (shadcn Sonner) on success or failure.
- Destructive actions (delete post/comment, leave group) use `ConfirmDialog` (shadcn AlertDialog).

## 8. Testing strategy

| Layer | Tool | Examples |
|---|---|---|
| Pure logic | Vitest | zod schemas, search escaping, error mapping, `redirectTo` sanitizer |
| Components | Vitest + RTL | forms show validation, ConfirmDialog flow, empty/error states, RequireAuth redirects |
| Data access | Vitest with mocked client | `api.ts` builds correct queries, never sends `author_id` |
| Authorization | pgTAP (`supabase test db`) | allowed **and** forbidden operations per role (see DATABASE.md §8) |
| Critical flows | Playwright on local stack | sign up → confirm (Inbucket) → join → post → comment → delete; signed-out redirect |

npm scripts: `typecheck`, `test`, `test:watch` and `test:e2e` exist (M1). `db:test` and `db:types` are added in M2. In M1, Playwright runs against the Vite dev server with mock data; from M2 it targets the local Supabase stack.

## 9. Deployment

- Vercel builds with `npm run build` and outputs `dist/`. `vercel.json` rewrites all paths to `/index.html` for client routing.
- `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY` are set in Vercel project settings. Both are safe to ship to browsers; security relies on RLS.
- Production migrations are applied with `supabase db push` **only after explicit approval**.

## 10. Key decisions (ADR summary)

| # | Decision | Why |
|---|---|---|
| 1 | No custom backend; RLS is the authorization layer | Fits the approved stack. One enforcement point that the client can't bypass. |
| 2 | `author_id` defaults to `auth.uid()`; clients get column-level INSERT grants that exclude it | Makes impersonation structurally impossible, with RLS as a second check |
| 3 | `is_group_member()` SECURITY DEFINER helper with `search_path = ''` | Avoids RLS recursion on `group_members` while staying minimal and hardened |
| 4 | Profiles hold only public fields; email stays in `auth.users` | Other users can read profiles, so nothing private belongs there |
| 5 | Profile rows created by DB trigger, not the client | Guarantees every user has a profile. No client INSERT grant needed. |
| 6 | `groups` separate from `universities`, with `UNIQUE (university_id)` | Matches the spec, enforces one group per university, and leaves room for group metadata |
| 7 | University data loaded by a reviewed migration generated from College Scorecard | Reputable public-domain source, reproducible, and the same data in every environment |
| 8 | Custom hooks rather than a data-fetching library | Fewer deps; the MVP's data needs are simple |
| 9 | Local Supabase (Docker) for development and tests | RLS tests never touch production |
| 10 | No UPDATE on posts/comments in the MVP | Smaller attack surface; editing isn't required |
